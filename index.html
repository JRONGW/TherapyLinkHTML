01 · Coursework rules & technology

Recommended stack: Python + Tkinter/ttk for a desktop UI, sqlite3 for local persistence, and unittest for tests. No Django, Flask, FastAPI, or equivalent ready-made application frameworks.

The COMP0066 brief allows either a command-line interface or a GUI, allows third-party libraries if sources are credited, encourages but does not require OOP, and focuses on core Python. Tkinter is a standard-library GUI toolkit, though GUI toolkits can be described as frameworks in some contexts; consult teaching staff if the prohibition is interpreted more broadly.

Demo account exception: The brief asks for usernames like patient1, mhwp1 with empty passwords to simplify marking. Use this only with synthetic coursework data, never in a real health application.

02 · Architecture

Keep GUI code, business logic, and database operations separate. The GUI calls services; services validate permissions and data, then use the database layer.

                         |

Booking flow

1. Request

Patient selects an MHWP time slot; the system validates dates, role and allocation.

2. Persist

Database transaction checks conflicts and saves a requested booking.

3. Confirm

MHWP confirms or cancels; both parties receive required notification.

03 · Six-person task allocation

Each person has a clearly owned area, but everyone should understand the shared database contract and test their own features.

PERSON 1 · DIFFICULTY 5/5

Database & data models

Owns: database/db.py, models.py, database tests

Build
  • Tables for users, allocations, appointments, moods, journals, notes, conditions and notifications.
  • CRUD operations and shared data access methods.
  • Persistent storage, foreign keys, transactions.
Learn

SQL SELECT/INSERT/UPDATE/DELETE, JOIN, constraints, Python classes, exceptions, sqlite3.

Watch out

Agree interfaces early; use parameterised SQL; enforce one MHWP per patient; test restart persistence.

PERSON 2 · DIFFICULTY 4/5

Login & administrator

Owns: admin/login.py, admin_views.py

Build
  • Login/logout and role-based navigation.
  • Admin overview, user editing/deletion.
  • Patient-to-MHWP allocation, current-week confirmed booking counts.
  • Disable/re-enable functionality.
Learn

Conditions, OOP, Tkinter buttons/entries/Treeview, callbacks, basic SQL.

Watch out

Disabled accounts can still log in/out but cannot use normal features or change data.

PERSON 3 · DIFFICULTY 4/5

Patient wellbeing features

Owns: patient_views.py, mood.py, journal.py, meditation.py

Build
  • Profile and emergency contact editing.
  • Colour-coded mood entry and comments.
  • Timestamped journal and history.
  • Keyword-searchable meditation resources.
Learn

Lists/dicts, searching/filtering, datetime, Tkinter Text/Listbox/Combobox, webbrowser.

Watch out

Protect patient privacy; save everything; use accurate colour code from brief; integrate Person 5's booking widget.

PERSON 4 · DIFFICULTY 4/5

MHWP records & dashboard

Owns: mhwp_views.py, dashboard.py, patient records

Build
  • Assigned-patient list and details.
  • Practitioner notes and predefined conditions.
  • Summary dashboard and per-patient mood charts.
Learn

JOIN/GROUP BY/COUNT, data aggregation, Tkinter Canvas/Treeview, modular OOP.

Watch out

Practitioners may access only their assigned patients; charts must match stored records.

PERSON 5 · DIFFICULTY 5/5

Appointments & notifications

Owns: booking.py, calendar.py, email_service.py

Build
  • MHWP calendar and available slots.
  • Patient request → MHWP confirmation/cancellation.
  • Double-booking prevention, email to relevant parties.
Learn

datetime, state machines, database transactions, Tkinter calendar, smtplib.

Watch out

Do not auto-confirm; reject past/overlapping bookings; do not claim email sent unless it really was.

PERSON 6 · DIFFICULTY 5/5

GUI, validation & integration

Owns: main.py, app.py, widgets.py, validation.py, shared tests

Build
  • Main window, role navigation and shared widgets.
  • Consistent forms and validation messages.
  • Integration tests and release packaging.
Learn

Modules/imports, OOP/composition, Tkinter geometry managers, unittest, Git.

Watch out

Do not become the only debugger: all six members own tests and fixes for their modules.

05 · Agree interfaces before coding

Many integration bugs are caused by different function names or incompatible return types. Agree on a contract for each function before development.

Proposed functionInputsExpected result
authenticate()username, passwordUser record or None
get_user()user IDUser record or None
get_allocation()patient IDAssignment or None
get_patient_moods()patient IDList of mood records
add_journal()patient ID, textNew entry ID
request_appointment()patient ID, MHWP ID, timeBooking ID
confirm_appointment()booking ID, MHWP IDUpdated booking
cancel_appointment()booking ID, actor IDUpdated booking

These are suggested method contracts, not guaranteed matches for existing files. Specify exact dictionary keys or dataclass fields together.

Example: parameterised database query

def get_patient_moods(self, patient_id):
    cursor = self.connection.execute(
        """SELECT mood_date, level
           FROM moods
           WHERE patient_id = ?
           ORDER BY mood_date""",
        (patient_id,)
    )
    return cursor.fetchall()
The person building patient screens calls database.get_patient_moods(patient_id) without duplicating SQL inside the UI.

06 · Four-week workflow & Git

Week 1 · Define contracts and skeleton

Database schema; shared method signatures; main Tkinter shell; UI wireframes; appointment states.

Week 2 · Build modules

Database, admin, mood/journal, MHWP records, booking, shared widgets/validation.

Week 3 · Integrate and test

Connect screens to persistence, test real workflows and errors, implement genuine email delivery where feasible.

Week 4 · Fix and demonstrate

Regression tests, fresh-install validation, cleaned ZIP, 5–7-minute video and peer evaluation.

09 · Submission checklist

Group: Submit a single groupNN.zip (maximum 50MB) with the Python source, and provide a MediaCentral demonstration video link in a .txt file via Moodle. Video length: 5–7 minutes, showing installation and application features rather than code walkthrough.

Individual: Every member completes the required IPAC peer evaluation on Moodle. Make individual contributions visible through commits, feature ownership, tests and review.

Recommended final package

groupNN.zip
  main.py
  therapylink/        # Python source modules
  tests/              # Automated tests
  README.md           # Installation and usage
  requirements.txt    # Only if extra packages used
  demo_data/           # Synthetic seed data or script

Prioritise correctness and test coverage over decoration. A reliable, modular application is better than an elaborate GUI with broken persistence or appointment logic.
